# ADR-001: 상태 관리와 라우팅으로 Riverpod + GoRouter 채택

> 예시입니다. 실제 프로젝트 ADR을 일반화해서 옮겼습니다.

- **상태**: Accepted
- **날짜**: 2026-07-14

## 결정

상태 관리와 DI는 Riverpod, 라우팅은 GoRouter를 쓴다. ViewModel과 그 하위 의존성(UseCase, Repository)은 모두 Provider로 등록하고 `ref.watch` / `ref.read`로만 가져온다.

## 배경

- 화면이 늘면서 의존성을 어디서 만들고 어디서 교체하는지가 화면마다 달라졌다.
- 테스트에서 의존성을 갈아끼우는 방식이 통일되지 않아 에이전트가 테스트를 쓸 때마다 다른 방식을 골랐다.
- 로그인 여부에 따라 진입 가능한 화면이 달라지는데, 이 판단이 화면 안에 흩어져 있었다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| Provider + Navigator 2.0 직접 구현 | 의존성이 적다 | 라우팅 코드가 많고 직접 유지해야 한다 |
| BLoC + auto_route | 이벤트 흐름이 명확하다 | 보일러플레이트가 많고 코드 생성 의존이 커진다 |
| **Riverpod + GoRouter** | DI와 상태를 한 도구로, 테스트 시 `overrides`로 교체 | Provider 범위를 잘못 잡으면 상태가 의도보다 오래 산다 |

## 결정 이유

- DI와 상태 관리를 한 도구로 묶으면 "의존성은 어디서 오는가"에 답이 하나가 된다. 에이전트가 따를 규칙이 단순해진다.
- 테스트는 `ProviderScope(overrides: [...])` 한 가지 방식으로 통일된다.
- 로그인 여부 같은 진입 조건은 GoRouter의 `redirect` 한 곳에서 판단한다.

## 결과

- Provider 트리 밖에서 인스턴스를 직접 만들지 않는다. → `AGENTS.md` Invariant로 올림
- Provider 범위(autoDispose 여부) 판단 기준을 코딩 컨벤션에 추가해야 한다.
- 화면 진입 조건이 바뀌면 화면이 아니라 라우터를 고친다.
