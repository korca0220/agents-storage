# Invariant 예시

> 실제 Flutter 모노레포에서 쓰던 규칙을 일반화했습니다. 프로젝트에 맞는 것만 골라 `AGENTS.md`에 옮깁니다.

Invariant 표에는 **규칙과 강제 수단만** 적습니다. 근거, 예외, 상세 절차는 ADR이나 스킬에 두고 링크합니다. 강제 수단이 도구(lint, 테스트, `.gitignore`)인 규칙은 자동으로 잡히고, "문서"인 규칙은 에이전트와 리뷰어가 지켜야 합니다. 가능하면 도구 쪽으로 옮기는 것이 좋습니다.

| # | 규칙 | 강제 수단 |
| --- | --- | --- |
| 1 | `packages/*`는 `apps/*`를 참조하지 않는다 (역방향 의존 금지) | 문서 — ADR |
| 2 | 코드 생성 결과물(`*.g.dart`, `*.freezed.dart` 등)은 직접 수정하지 않는다. 생성 명령으로 재생성한다 | 생성 명령 |
| 3 | API 클라이언트 생성 결과물은 커밋하지 않는다 | `.gitignore` |
| 4 | API 추가/수정은 `api-creator` 스킬을 거친다 | 문서 — ADR |
| 5 | Entity, VO 생성과 수정은 `entity-creator` 스킬을 거친다 | 문서 — ADR |
| 6 | 단위 테스트는 `test-code-creator` 스킬 규칙을 따른다 | 문서 |
| 7 | ViewModel과 그 하위 의존성은 DI 컨테이너(Provider)로 등록하고 거기서만 가져온다. 테스트는 override로 교체한다 | 문서 — ADR |
| 8 | UseCase, Repository는 `Result<T>`를 반환하고 호출측에서 성공/실패 분기를 명시한다. 그 밖에서는 `Result`를 반환값으로 쓰지 않는다 | 문서 — ADR |
| 9 | `domain/` 레이어는 순수 언어 코드를 유지한다. `data/`, `presentation/`, UI 프레임워크를 import하지 않는다 | import lint |
| 10 | 코드 변경 PR을 열기 전 품질 게이트를 로컬에서 통과시킨다 | 문서 — `CONTRIBUTING.md` |

## 규칙을 올리는 기준

- 리뷰에서 같은 지적이 두 번 나왔다.
- 어기면 되돌리기 어렵다 (레이어 오염, 생성 파일 수정).
- 에이전트가 더 "흔한" 방식으로 바꾸자고 반복해서 제안한다.

한 번 나온 지적은 코딩 컨벤션으로, 반복되고 비용이 큰 것만 Invariant로 올립니다.
