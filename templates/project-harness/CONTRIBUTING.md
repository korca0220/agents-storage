# CONTRIBUTING — 커밋, PR 작성 규칙

사람과 에이전트 공통 규칙입니다. 에이전트는 첫 커밋 또는 PR 작성 전에 이 문서를 읽습니다 (훅이 있으면 자동으로 주입됩니다).

## PR 본문

PR 본문은 `.github/PULL_REQUEST_TEMPLATE.md`의 구조를 따릅니다. 웹 UI는 템플릿을 자동 적용하지만 `gh pr create` 같은 CLI는 본문을 직접 구성해야 합니다.

### 리뷰어를 위한 브리핑

PR 본문은 작업 일지가 아니라 **리뷰어가 변경을 이해하고 확인하기 위한 브리핑**입니다. 정보는 아래 중 하나에 해당할 때만 넣습니다.

- 변경의 목적과 결과를 이해하는 데 필요하다.
- 구현의 정확성이나 위험을 리뷰하는 데 필요하다.
- 중요한 설계 판단과 그 영향을 이해하는 데 필요하다.
- 변경된 동작을 직접 확인하는 데 필요하다.

빼는 것:

- 작업을 진행한 시간순 기록, 모든 커밋과 파일의 변경 목록
- 최종 결정에 영향을 주지 않은 조사 과정
- 에이전트명, 생성 도구 표기, 세션 URL 등 리뷰와 무관한 흔적

결론을 먼저 씁니다. 한 목록 항목에는 한 주장만 담습니다.

### 섹션

| 섹션 | 역할 |
| --- | --- |
| {{중점 포인트}} | 이것만 읽어도 목적, 핵심 변화, 중요한 판단이 이해되게 |
| {{Content}} | 전체 작업 범위를 기능, 관심사별로 묶어서 |
| {{Issues}} | 알려진 제한, 머지 순서, 필수 후속 작업. 없으면 `해당 없음` |
| {{How To Test}} | 리뷰어가 재현하는 절차와 기대 결과 |
| {{References}} | 이슈, 디자인, exec-plan, ADR 링크 |
| {{Attachments}} | UI 변경이면 Before / After |

## PR 제목

- `<type>(<scope>): <설명>` 또는 `<type>: <설명>`
- 예: `{{feat(app): 로그인 화면 추가}}`

## 라벨

- 타입: {{Feat / Fix / Refactor / Docs / Chore}}
- 영역: {{...}}

## 베이스 브랜치, 이슈 연결

- 기본 베이스 브랜치: `{{develop}}`
- 이슈 트래커: {{Linear / Jira / GitHub Issues}}. 브랜치명 접두: `{{ISSUE-123}}-설명`

## 커밋 메시지

- `<type>: <설명>` 또는 `<type>(<scope>): <설명>`
- `type`: `feat` / `fix` / `refactor` / `docs` / `chore`
- `scope`: 변경이 특정 패키지에 한정될 때만 씁니다. 여러 곳에 걸치거나 하네스 변경이면 생략합니다.

## 커밋 단위

- 하나의 커밋은 하나의 논리적 변경을 담고, 그 시점에 빌드와 분석이 통과해야 합니다.
- 파일 이동은 `git mv`로 하고 내용 변경과 분리합니다.

## PR 전 품질 게이트

코드 변경이 있는 PR은 아래를 로컬에서 통과시킵니다. 이 목록의 정본은 이 문서입니다.

```bash
{{의존성 설치}}
{{코드 생성}}
{{lint}}
{{format 검사}}
{{test}}
```

Flutter + Melos 예시는 [`examples/quality-gate-flutter-melos.md`](./examples/quality-gate-flutter-melos.md)에 있습니다. (적용 후 이 링크는 지웁니다.)
